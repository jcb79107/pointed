# Route cleanup and performance audit — October 13, 2026

Local branch: `fix/clean-routes-performance`, based on `5d4c6ff`. No deployment, push, schema change, dependency addition, or production configuration change.

## Journey and acceptance criteria

The main journey is landing → connect Linear → choose a team/cycle → preview and reorder tickets → run a session → save estimates. The public demo provides a signed-out pointing journey.

- Visible navigation uses clean URLs; old bookmarks and OAuth return destinations still work, including query strings.
- Signed-out protected pages still require authentication. Session authorization and invitation links stay intact.
- Reduce demonstrated unnecessary work without changing vote behavior, freshness, or feedback consent.
- Verify narrow and wide layouts, keyboard/accessibility checks, feedback recording, and recovery after a hidden/offline tab returns.

The stack is Next.js App Router, React, Drizzle/Neon, Pusher, and Sentry. Existing server rendering, static landing output, route splitting, compressed assets, parallel independent queries, and lazy ticket media already help. No image or font optimization problem was demonstrated in the measured pages.

1. **Load the feedback recorder only when requested.** The recorder was downloaded on every entry page even though recording was off. It now loads after an explicit recording request. Error reporting remains available immediately. Masking, blocked fields, and upload-on-send behavior are preserved. Loading feedback and cancellation prevent a delayed download from starting recording after consent is withdrawn. Calling Sentry's `getReplay()` from ordinary feedback code also imported the recorder; looking up the installed integration avoids that dependency.
2. **Stop fallback polling in hidden/offline rooms.** The five-second fallback now runs only for visible, online viewers. Existing Pusher updates and immediate visibility/online recovery remain. In a controlled 16-second hidden-state window, snapshot requests fell from **3 to 0**. Automated tests also verify visible polling and immediate recovery.

The same fake Sentry DSN enables equivalent SDK behavior in both builds; no real telemetry was sent.

The strongest result is about **39 KB less initial compressed JavaScript per page**: roughly 16% on landing and 12% on the demo. Bundle inspection identified the deferred recorder chunk at 39,344 gzip bytes. Navigation load improved by 134–172 ms in this small local sample. This is actual measured load reduction, not proof of a noticeable field improvement. The new recorder loading state is a perceived responsiveness improvement, not a faster recorder download.

CLS was 0 before and after. Demo click-to-visible-estimate measurements were 100 → 79 ms on desktop and 66 → 74 ms on mobile; there is **no demonstrated consistent interaction-speed improvement**. This test is not INP. Observed long-task excess decreased, but its measurement window is not Lighthouse TBT, so no standardized TBT claim is made.

Raw JSON, screenshots, and the measurement harness are in local `output/performance/`: `before.json`, `after.json`, `summary.json`, `measure.mjs`, and `polling.mjs`. To repeat the after measurement with an equivalent production server on port 3002:

## Server/database investigation

A read-only diagnostic exercised the existing database transport/security wrapper with role inspection, a read-only transaction, an empty transaction-local session hash, `select 1`, and commit. It read no tenant records and wrote no application data. Four samples were 747, 115, 118, and 114 ms from this laptop. The first request was slower; warm wrapper overhead was about 115 ms. These are not timings for actual session queries or Vercel requests.

Source inspection shows several scoped queries per snapshot and relationship requests during Linear issue import. Independent work is already parallelized in places. The role check and transaction-local identity enforce isolation; weakening them for speed would be inappropriate. No evidence justified a new index, cache, or database architecture change.

## Remaining investigations, ranked

1. **Potentially highest impact: authenticated large-cycle import and live snapshot latency.** Capture real request traces and query timings with a disposable workspace before choosing an optimization. The laptop transport probe suggests round trips deserve attention, but does not prove production query slowness. Real Linear writes and a live multi-user session were not exercised in this audit.
2. **Scale risk: growing session history and large queues.** Session history is unbounded; cycle import has a 1,000-issue limit and relationship-fetch fan-out. The small fixture did not demonstrate a problem. Measure realistic larger datasets before adding pagination, virtualization, or bulk-fetch changes.
3. **Lower priority: shared CSS and remaining framework JavaScript.** Shared CSS is about 26 KB compressed, and framework/runtime code remains a substantial part of JS. No measured issue warrants a stylesheet or framework rewrite.

## Measurement limits

Local production builds are not the production hosting environment. Browser throttling is not a physical mobile device, and three runs do not establish statistical significance or real-user p75 Core Web Vitals. Navigation load is the browser load event, not a complete usability measure. The sign-in page was measured without authenticating; queue/live-room coverage uses isolated fixtures and intercepted requests, not a live Linear integration. Large ticket images, real customer data, production query plans, hosting-region latency, and real-user INP were not measured. The hidden-state measurement controls document visibility rather than relying on operating-system background throttling.
